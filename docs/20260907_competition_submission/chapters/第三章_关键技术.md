# 第三章 关键技术：章节材料包

## 3.1 Swarm-LIO 算法原理

### [可直接写但需限定] 参考算法原理

本地归档的 Swarm-LIO2 论文和源码为本节提供了算法原理来源。该方法采用分布式、即插即用和低带宽的集群状态估计架构：每架无人机独立估计自身状态，同时交换低维的身份、自状态、互观测和全局外参信息，以完成自状态与队友相对状态估计。初始化阶段通过激光反射强度/几何信息检测队友，结合轨迹匹配识别新成员，并通过因子图优化估计全局外参；在线阶段在误差状态迭代卡尔曼滤波（ESIKF）中融合 LiDAR、IMU 和互观测信息，对异步测量进行时间补偿，并通过队友状态边缘化和退化评估控制集群规模增长带来的计算量。

归档源代码中的对应接口包括 `Multi_UAV::QuadstateCbk`、`GlobalExtrinsicCbk`、队友轨迹/簇提取、`ESIKF` 预测更新、`PublishQuadstate` 和 `PublishGlobalExtrinsic`；消息定义 `QuadStatePub.msg`、`GlobalExtrinsicStatus.msg` 描述了自状态、协方差、速度、退化标志、观测队友和外参状态。

### [可直接写但需限定] 本项目中的感知链

在本项目中，LIO 位于感知闭环前端：点云和 IMU 经过时间同步、去畸变/配准和状态估计，输出可供探索规划使用的位姿、点云和占据地图。多机系统在此基础上维护共享异步地图，使每一架无人机既能使用自身观测，也能根据通信状态接收队友的地图/任务状态。

正式三机仿真采用 `registration_source=gt`，目的是先隔离任务分配、共享地图、轨迹规划和容错机制；它不是对真实 Swarm-LIO 误差的测量。真实双机专项审计则检查了 LIO、MAVROS local position、外部视觉输入和 planner frame 的连接关系，但目标 18:32 会话缺少 runroot，较早候选会话被判为 `INVALID_RUN`。

## 3.2 RACER 与单机优化

### [可直接写] 单机探索闭环

RACER/探索管理器以占据栅格和 frontier 为输入，在规划边界内选择未知区域候选点，结合路径代价、信息增益和安全约束生成下一目标；随后通过 A*/kinodynamic 搜索和 B-spline/轨迹优化生成可执行轨迹，交给 trajectory server 和飞控执行。FSM 中设置了 frontier 定时检查、replan 触发、路径失败重试、回退以及避碰/返航条件。

代码中可以直接核验的实现线索包括：`frontierCallback` 约 0.5 s 定时器、`/planning/replan` 和 `/planning/new` 话题、`fsm/replan_time` 与多个 replan threshold、pair-opt 请求/响应话题以及 `sim_drop_rate` 丢包注入参数。

### [可直接写但需限定] 感知范围和防冻结思路

阶段材料记录了从约 4–5 m 有限深度感知向约 20 m 水平 360° Mid-360 感知的升级；单机探索部分加入了从当前里程计状态软重规划、无 frontier 时周期性复查、路径失败重试和安全边界检查等机制。代码与 overlay 中还保留了防冻结、重复 frontier 和轨迹安全相关修改线索。

这些机制可以作为“设计和单机基线”写入，但论文不能把历史长跑中手动停止、地图缺失或未形成正式 runroot 的记录包装成完整 endurance 指标。

### [可直接写] 任务分配目标

多机 frontier/网格分配支持 `MINSUM` 与 `MINMAX` 目标，并通过 `capacity_factor` 表示单机容量约束；pair-opt 用于在队友状态发生变化时协调网格归属。正式 P0 矩阵显示，MINMAX 在无掉线 A2 组的负载不均衡和 Jaccard 指标上优于部分 MINSUM/故障组配置，具体数据在第四章和 `experiments/REPORT_P0_MATRIX_CLOSEOUT.md`。

## 3.3 自适应弹性决策

### [可直接写但需限定] 掉线检测、任务释放和接管

掉线机制的基本流程是：检测队友心跳/状态异常，释放其未完成任务，由其他无人机按最近邻或候选代价接管，再继续 frontier 探索。报告记录了 3-UAV 仿真中“检测—release—nearest takeover—continue”的连续流程，并区分 intentional dropout 与 unexpected loss。

### [可直接写但需限定] 20% 任务层丢包

代码提供 `fsm/sim_drop_rate` 参数，按消息概率注入任务层丢包；pair-opt 相关实现包含消息时间戳判断、重复/幂等应答和重试统计，报告还记录了 heartbeat/self-heal 思路。300 s 报告对比中，0% 基线覆盖率为 0.673，20% 注入覆盖率为 0.657，比例约 97.6%，无 crash。

必须明确这不是无线链路实测，也不是 Linux `tc` 等底层网络吞吐测试。当前可精确定位的 `results/RUN-20260827T040141Z-3uav-verify-droploss20-90s/` 是另一次短时检查，不能替代报告中的 300 s run32/run33 原始证据。

### [需限定/留空] 子系统失效和 2 s 重规划

`experiments/子系统失效改动.md` 提出通信、定位、建图、规划、执行五维健康状态，以及 `HEALTH_HOLD`、任务广播/回收/恢复流程；当前材料更接近设计与部分实现说明，缺少完整故障注入矩阵和每种故障的恢复统计。题目要求的“在线重规划响应不超过 2 s”也没有可审计的事件时间戳—新轨迹生效时间差，因此本项留空待补。
