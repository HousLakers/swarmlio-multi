##  丢包模拟方案

第一阶段建议优先在 RACER 的任务协商层模拟丢包，而不是直接使用 Linux `tc netem loss 20%` 对底层网络进行随机丢包。

原因是 ROS1 中大量通信基于 TCPROS，底层网络数据包丢失后 TCP 可能自动重传，不能直接等价于“任务消息丢失”。本阶段真正需要观察的是 `pair_opt` 与 `pair_opt_res` 这类应用层协商消息被丢弃后，对任务分配产生的影响。

### 第一阶段：仅丢弃 `pair_opt_res`

首先只对响应消息设置 20% 随机丢弃：

```cpp
double r = uniform01(rng);

if (r < 0.20) {
  ROS_WARN("[packet_loss] drop pair_opt_res");
  return;
}

pair_opt_res_pub_.publish(msg);
```

建议增加参数：

```text
packet_loss/enabled = true
packet_loss/response_loss_rate = 0.20
packet_loss/random_seed = 20260824
```

固定随机种子可以保证优化前后使用同一组丢包序列，使实验结果具有可重复性。

该阶段主要用于精确复现：

```text
请求成功到达
+
响应随机丢失
→
双方任务状态不一致
```

### 第二阶段：请求与响应均设置 20% 丢包

在第一阶段验证完成后，再扩展为：

```text
pair_opt      → 20% 丢包
pair_opt_res  → 20% 丢包
```

此时既可能出现请求未到达，也可能出现响应未到达，更接近一般无线通信不稳定条件。

### 第三阶段：丢包 + 随机延迟

进一步加入 50～300 ms 等随机通信延迟，用于模拟：

```text
旧消息晚到
消息乱序
不同无人机收到信息的时间不一致
```

该阶段主要用于验证后续设计的版本号机制。

### 第四阶段：连续丢包

模拟一段时间内连续丢失若干消息，例如连续丢失 2～5 个任务协商包，用于模拟墙体遮挡、转弯、局部无线信号衰减等情况。


## 3. 改进方案一：增加 PENDING 中间状态

### 3.1 原有逻辑

原流程为：

```text
接收 pair_opt
      ↓
计算新的任务划分
      ↓
立即修改 grid_ids
      ↓
发送 pair_opt_res
```

问题在于接收方“修改任务”发生得过早。

### 3.2 改进逻辑

建议增加一个任务预留状态：

```text
OLD
 ↓
PENDING
 ↓
COMMITTED
```

具体流程：

```text
收到 pair_opt
      ↓
计算新的任务划分
      ↓
保存为 pending_grids
      ↓
暂不修改正式 grid_ids
      ↓
发送 ACCEPT
      ↓
收到最终 COMMIT
      ↓
正式修改 grid_ids
```

接收方收到请求后只暂存新的任务结果，不立即开始执行新的任务。

这样即使响应包丢失，也不会立即造成一侧已经采用新任务、另一侧仍使用旧任务的永久分裂。

## 4. 改进方案二：为每次协商增加 transaction_id

现有系统可以通过重复发送提高消息送达概率，但如果没有唯一标识，重复收到同一条消息可能被误认为新的任务交换。

因此建议每次任务协商生成唯一：

```text
transaction_id
```

例如：

```text
transaction_id = 137
sender = UAV1
receiver = UAV2
```

接收方记录最近处理过的 transaction：

```cpp
if (msg.transaction_id == last_transaction_id) {
  resendResponse();
  return;
}
```

也就是说：

```text
第一次收到 transaction 137
→ 正常计算任务

第二次、第三次再次收到 137
→ 不重新计算
→ 不重复修改任务
→ 只重新发送相同响应
```

这样可以保证任务协商具有**幂等性**：同一条消息收到一次或收到十次，最终结果相同。

## 5. 改进方案三：增加任务版本号 epoch

`transaction_id` 主要解决重复消息问题，但不能解决旧消息延迟到达的问题。

因此建议为任务分配状态增加单调递增的：

```text
task_epoch
```

例如：

```text
epoch = 31
owner = UAV1

重新分配后：

epoch = 32
owner = UAV2
```

如果网络延迟导致旧消息后来才到：

```text
epoch = 30
```

接收方直接忽略：

```cpp
if (msg.epoch < local_epoch) {
  return;
}
```

这样可以避免：

```text
已经采用新任务
      ↓
旧消息晚到
      ↓
任务又被错误改回旧状态
```

`epoch` 可以同时帮助处理：

- 随机丢包；
- 消息重传；
- 网络延迟；
- 消息乱序；
- 旧响应包晚到。

## 6. 改进方案四：将任务交换改为 PROPOSE—ACCEPT—COMMIT

建议将原来的“两步任务交换”改为三阶段协议：

```text
PROPOSE
   ↓
ACCEPT
   ↓
COMMIT
```

完整过程如下：

```text
无人机 A                         无人机 B

PROPOSE
------------------------------>
                                计算新任务
                                保存为 PENDING

<------------------------------
ACCEPT

A 收到 ACCEPT
确认该方案

COMMIT
------------------------------>
                                正式修改 grid_ids
```

不同消息丢失时：

### PROPOSE 丢失

```text
A 未收到任何响应
→ 超时后重发相同 transaction_id
```

### ACCEPT 丢失

```text
A 未收到 ACCEPT
→ 重发原 PROPOSE

B 发现 transaction_id 已处理
→ 不重新计算
→ 只重新发送 ACCEPT
```

### COMMIT 丢失

```text
B 保持 PENDING
→ A 周期性重发 COMMIT
→ B 最终完成正式更新
```

该机制不能保证通信永远瞬时一致，但能够显著降低一次响应包丢失造成永久任务分叉的风险。

## 7. 改进方案五：周期性任务状态校正

仅依赖一次握手仍不足以处理长期不稳定通信。

建议利用现有 `DroneState` 广播机制增加轻量的任务状态摘要，例如：

```text
drone_id
task_epoch
grid_ids
health_status
```

每架无人机周期性广播当前任务状态：

```text
UAV1:
epoch = 32
grid_ids = {1, 5, 8}

UAV2:
epoch = 34
grid_ids = {2, 3, 7}
```

接收方发现：

```text
remote_epoch > local_epoch
```

则说明自身状态已经过期，需要重新同步。

如果某一次 PROPOSE、ACCEPT 或 COMMIT 全部丢失，周期性任务状态广播仍然可以作为“第二道保险”，使系统在后续通信恢复后重新收敛。

因此整体思想不是要求：

> 每一条任务交换消息必须成功。

而是要求：

> 即使部分消息丢失，任务状态最终仍能够自动恢复一致。

## 8. 改进方案六：区分短时丢包与真正掉线

20% 丢包环境下，如果只要一个心跳没有收到就立即判断无人机掉线，会出现大量误判。

因此建议将通信状态划分为：

```text
ONLINE
  ↓
SUSPECT
  ↓
OFFLINE
```

例如：

```text
短时间未收到心跳
→ SUSPECT
→ 暂时不给该无人机分配新任务
→ 但不立即回收其已有任务

持续超过失联阈值
→ OFFLINE
→ 正式回收任务
```

这样可以避免随机丢包被误认为真正的无人机故障。

无人机恢复通信后：

```text
OFFLINE
   ↓
RECOVERING
   ↓
同步最新 epoch / grid_ids
   ↓
ONLINE
   ↓
重新通过 pair_opt 获取任务
```

恢复机不能直接继续执行掉线前保存在本地的旧任务，否则可能重新造成重复覆盖。


| 改进方式                   | 对探索/建图效率       | 对功耗         | 主要代价            |
| ---------------------- | -------------- | ----------- | --------------- |
| `transaction_id`       | 几乎无影响，甚至有利     | 几乎无影响       | 多存一个编号、做一次比较    |
| `epoch`                | 几乎无影响，能减少错误回退  | 几乎无影响       | 多比较一个版本号        |
| `PENDING`              | 可能轻微降低瞬时效率     | 可能轻微增加      | 等确认期间任务暂不执行     |
| PROPOSE–ACCEPT–COMMIT  | 丢包严重时会增加任务交换延迟 | 可能增加通信和悬停能耗 | 多一次通信过程         |
| 周期状态同步                 | 很小；同步太频繁才会影响   | 通信/CPU略增    | 周期广播额外消息        |
| ONLINE/SUSPECT/OFFLINE | 掉线后任务接管会稍慢     | 可能多消耗一些时间   | 为避免误判，要等待确认真的掉线 |
| RECOVERING             | 恢复后短暂不能立即探索    | 很小          | 先同步再重新接任务       |
